# @contour-ui/tokens

**Layer 0 — foundation.** Design tokens in [DTCG 2025.10](https://www.designtokens.org/tr/2025.10/)
format, compiled into CSS custom properties, typed TS references, token data and, for Soundor,
the values themselves.

- **May depend on (internal):** nothing.
- **Token reference:** the Tokens page of the docs (`/docs/guide/tokens`) shows every custom
  property with its value and alias per theme, built from `docs.json`.

## Usage

```ts
import '@contour-ui/tokens/tokens.css'; // once, before @contour-ui/react/styles.css
import { vars } from '@contour-ui/tokens';

vars.color.bg.surface; // 'var(--ct-color-bg-surface)'
```

```css
.panel {
  padding: var(--ct-space-panel-inset);
  background: var(--ct-color-bg-surface);
  color: var(--ct-color-fg-default);
  font: var(--ct-text-body); /* font shorthand; letter-spacing is separate */
  letter-spacing: var(--ct-text-body-letter-spacing);
}
```

- **Themes:** dark is the default (`:root`, `[data-theme="dark"]`); `[data-theme="light"]` on
  any element switches its subtree. `themes`, `defaultTheme` and `themeAttribute` are exported.
- **Base vs semantic:** `--ct-base-*` (raw palette and scales) is emitted because semantic
  roles reference it, but it is internal: components use semantic roles only, and
  `vars` exposes only those.
- **Fonts:** `--ct-base-font-family-*` names IBM Plex Sans and JetBrains Mono; the font files,
  for every `--ct-base-font-weight-*`, are in `@contour-ui/fonts` (`@contour-ui/fonts/fonts.css`
  on the web), so this package downloads none.
- **Typography:** each text style is `--ct-text-<style>` (`font` shorthand) plus
  `--ct-text-<style>-font-family | -font-size | -font-weight | -line-height | -letter-spacing`.
  The dense plugin styles (`heading`, `body`, `label`, `label-lg`, `value`, `caption`) have
  long-form companions for docs pages: `display`, `title`, `subtitle` (h1–h3), `prose` and `code`;
  site pages such as a home page add `hero` (the 60 px title), `lead` (the paragraph under it) and
  `nav` (the links of the site header).
- **Control sizes:** `--ct-size-control-sm | -md | -lg` are the heights of controls. `sm` and `md`
  share the label (`--ct-text-label`), the side padding (`--ct-space-control-inset`) and the gap
  between icon and label (`--ct-space-control-gap`); `lg` has its own: `--ct-text-label-lg`,
  `--ct-space-control-inset-lg` and `--ct-space-control-gap-lg`.
- **Code highlighting:** `--ct-color-syntax-<name>` uses the names of Shiki's `css-variables`
  theme (`--shiki-token-<name>`); every one is at least 4.5:1 on `bg-inset`, the code block
  background.
- **Shadows, layers:** `--ct-shadow-<name>` is a `box-shadow` list (DTCG `shadow`, stronger in the
  dark theme); `--ct-layer-<name>` is a `z-index`.

## Soundor

Soundor styles are objects without CSS, so `@contour-ui/tokens/soundor` holds the values of every
semantic token per theme, as they take them:

```ts
import { soundorTokens } from '@contour-ui/tokens/soundor';

const { color, radius, text } = soundorTokens.dark;
color.bg.surface; // '#16191c'
radius.panel; // 8
text.label; // { fontFamily: 'IBM Plex Sans', fontSize: 11, fontWeight: 500, lineHeight: 13.2, letterSpacing: 0.5 }
```

- **Colors** are hex, with 8 digits for a translucent role (`overlay.scrim`).
- **Lengths** are px and **durations** ms, as numbers.
- **Text styles** are the style properties of a Soundor `Text`: the first family of the stack
  (Soundor takes one) and the line height in px.
- **Transitions** are `{ duration, easing, delay }`, with the named easing closest to the curve
  (Soundor has no `cubic-bezier()`).
- **Shadows** have no Soundor equivalent and are left out.

## Token data

`@contour-ui/tokens/docs.json` lists every custom property of `tokens.css` with its resolved value
and alias in each theme, for token references such as the Tokens page of the docs site:

```ts
import docs from '@contour-ui/tokens/docs.json' with { type: 'json' };

docs.tokens.find((doc) => doc.name === '--ct-color-bg-surface');
```

```json
{
  "$description": "Generated by @contour-ui/tokens-compiler from contour.resolver.json. Do not edit.",
  "tokens": [
    {
      "name": "--ct-color-bg-surface",
      "token": "color.bg.surface",
      "type": "color",
      "part": null,
      "description": "Panels and sections placed on the canvas.",
      "themes": {
        "dark": { "value": "oklch(0.21 0.008 255)", "alias": "--ct-base-color-neutral-950" },
        "light": { "value": "oklch(1 0 0)", "alias": "--ct-base-color-neutral-0" }
      }
    }
  ]
}
```

| Field         | What it holds                                                                                                                            |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `name`        | the custom property, `--ct-…`                                                                                                            |
| `token`       | the DTCG path of the token it comes from, such as `color.bg.surface` or `text.label`                                                     |
| `type`        | the DTCG type: `color`, `dimension`, `typography`, `shadow`, `transition`…                                                               |
| `part`        | the sub-value of a composite token: `font` (the shorthand of a text style), `fontSize`, `letterSpacing`…; `null` for a whole token       |
| `description` | the token's `$description`, or `null`                                                                                                    |
| `themes`      | per theme (`dark`, `light`): `value`, fully resolved, and `alias`, the custom property it refers to (`null` for literals and shorthands) |

Tokens come in the order of `tokens.css`, `--ct-base-*` included, since aliases point at them. The
file is generated with the CSS, so it changes with it.

## Sources

```
contour.resolver.json          DTCG resolver: sets (base, semantic) + theme modifier (dark default)
src/base/*.tokens.json         raw values: the palette and the scales
src/semantic/*.tokens.json     roles: color and shadow files per theme, the rest theme-independent
contrast.json                  the WCAG contrast targets of the color roles
vite.config.ts                 what the package ships and the checks of its build
scripts/design-system.ts       export for the Design System page
scripts/palette.ts             the formula of the palette, run by hand for changes across it
```

Every `*.tokens.json` is a source, edited by hand. A color is oklch, three numbers; `hex` is left
out, since the build derives what each platform needs.

## Build

`vp pack` writes everything the package ships into `dist`, nothing else: the `designTokens` plugin
of `@contour-ui/tokens-compiler` (private tooling, `tooling/tokens-compiler`) turns the sources into
a model and the model into `tokens.css`, the `index` and `soundor` entries and `docs.json`, as
`vite.config.ts` lists them. The workspace reads this `dist` like any consumer, so it is built
before anything that reads it: after an install (`prepare`), a pull or a branch switch (the git
hooks), and first in `vp run ready` and CI.

| Command                                                      | What it does                                        |
| ------------------------------------------------------------ | --------------------------------------------------- |
| `vp run @contour-ui/tokens#build`                            | build `dist`; a cache hit when no source changed    |
| `vp -C packages/tokens pack --watch`                         | rebuild on every source change, beside a dev server |
| `vp run --filter @contour-ui/tokens design-system <out-dir>` | export `tokens.json` for the Design System page     |
| `node packages/tokens/scripts/palette.ts`                    | rewrite the palette from its formula                |

The build is the test: it fails with every problem at once, each with its token and theme. Built
in: aliases point at tokens, every theme has the same tokens with the same types and descriptions,
names are kebab-case. `vite.config.ts` adds the WCAG contrast pairs of `contrast.json` in both
themes (a foreground `color.syntax.*` stands for every syntax role), a palette stop as light in
every hue, every color inside sRGB, and a `$description` on every semantic token, which the typed
entries carry as JSDoc and `docs.json` as `description`. The Soundor entry fails the build on a value Soundor
cannot take: a length not in px, a curve without a named easing.

The palette follows a formula: every hue shares one lightness curve, so a stop is equally light in
every hue and contrast pairs transfer between hues, and every color is gamut-mapped into sRGB and
written with the mapped color's own oklch coordinates. For a change across the palette,
`node packages/tokens/scripts/palette.ts` rewrites `src/base/color.tokens.json` from it; review
the diff like any other edit. DTCG aliases cannot change alpha, so a translucent role
(`overlay.scrim`) is a copy of its palette color with an alpha: keep it equal to that color.
